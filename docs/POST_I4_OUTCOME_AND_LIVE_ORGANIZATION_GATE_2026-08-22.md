## 1. Development rule

> **No major architectural expansion without measurable outcome evidence.**

I.1–I.4 established strong canonical autonomy/evidence prerequisites. They do not, by themselves, prove that Global Mobility AIOS can operate a useful professional mobility organization end to end.

The next development phase therefore prioritizes measurable mobility outcomes and a real operating organization over another broad governance abstraction.

This is a sequencing correction, not an architectural reversal.

Permanent trust boundaries remain intact:

```text
memory != truth
Capability != Authority != Autonomy != Risk
CAN DO != MAY DO
ELIGIBLE != permission
scores route; deterministic gates authorize
Human Owner / Board remains supreme
external frameworks provide capability, not semantic sovereignty
```

## 2. Acceptance equation

Future product claims must increasingly satisfy four distinct forms of proof:

```text
Software correctness
+
Governance correctness
+
Domain correctness
+
Real-world outcome correctness
=
AIOS acceptance
```

A green software test suite is necessary but is not evidence that an immigration conclusion is correct.

A correct immigration conclusion is necessary but is not evidence that a persistent multi-agent organization can deliver it reliably, economically and transparently.

The proof layers must remain separately inspectable.

## 4. Outcome Evaluation programme

The evaluation layer is measurement infrastructure, not canonical legal authority.

Gold/evaluation cases must carry explicit provenance classes:

```text
SYNTHETIC
PROFESSIONALLY_REVIEWED
HISTORICAL
LIVE_SHADOW
```

Synthetic cases are useful for harness correctness and adversarial coverage. They must never be represented as professional/legal validation.

A professionally reviewed or historical case must identify its review/evidence basis and evaluation-as-of boundary. Live-shadow cases must remain non-authorizing unless a separately governed workflow permits action.

Initial mobility metrics should include explicit numerators and denominators for:

```text
pathway identification accuracy
eligibility conclusion accuracy
evidence completeness / required-evidence recall
missing-evidence detection
rule/source citation correctness
contradiction detection
professional correction rate
human interventions per case
false escalation rate
missed escalation rate
```

As trustworthy labels and completed cases become available, add:

```text
document defect rate
RFI / authority-rejection rate
successful outcome rate
time per completed case
EUR per completed case
```

No universal scalar “mobility quality score” is authorized by this gate.

## 6. J → K → L organization proof

The canonical V1.3 sequence remains controlling.

### J — Agent Organization Runtime

Prove persistent AI employees can participate in one organizational task with native AIOS identity, authority, context and messaging semantics.

Initial proof must demonstrate at least:

```text
Client goal
→ Mission
→ persistent responsible position
→ delegated WorkItems
→ specialist collaboration
→ durable OrganizationActivity / conversation lineage
→ result returned to mission owner
```

Do not add a new agent framework merely to satisfy J. Candidate runtimes/donor patterns must show a measurable gap versus native AIOS execution.

### K — Execution / Coworker Runtime

Add only the bounded execution capabilities needed by the selected real mobility slice, behind AIOS-owned adapters and authority controls.

Examples may include official-source retrieval, documents/files and other tools required by the benchmark. Do not prebuild the complete future tool estate.

### L — Live Organization

L requires **real runtime organizational activity, not simulated dashboard data**.

The proof should expose:

```text
Mission
agents / persistent positions
WorkItems
collaboration
blocked work
material decisions
Evidence / rule lineage
tool activity
incidents / escalation
autonomy state
cost
latency
quality / outcome metrics
```

in the Global Mobility AIOS Cockpit / transparency surfaces.

## 7. Governance overhead budget

Governance must prove that it enables safe autonomy rather than becoming bureaucracy.

Adopt the Governance Amplification Factor (GAF):

```text
GAF = governed completion cost / minimally viable raw task cost
```

GAF must be reported by risk tier and workflow. A single organization-wide value may hide excessive overhead in R0/R1 work.

Cost attribution should distinguish where measurable:

```text
primary inference
Context Broker assembly
independent verification
deterministic governance
execution/tools
retry + stale-work loss
observability/storage
human/professional intervention
```

Target principle remains:

> **Governance Cost ∝ Risk × Uncertainty × Novelty**

R0/R1 should stay close to the minimally governed path. R4/R5 may justify materially higher amplification.

## 9. Context Broker adversarial proof

Before broad Live Organization dependence, Context Broker evaluation must intentionally test:

```text
mandatory Evidence omitted
stale rule/source supplied
known contradiction omitted
malicious or instruction-bearing retrieved content
cross-case contamination
cross-tenant contamination
outdated conversation/decision summary
missing authority/autonomy/risk constraints
irrelevant context flooding
```

Desired behavior is governed uncertainty, blocking, refresh or escalation where required.

The benchmark must not reward a model for improvising around missing canonical truth.

Retrieved knowledge remains data, not executable authority.

## 10. Recovery and irreversible workflow proof

Move recovery proof from generic contracts into selected mobility workflows.

For each material action, classify the consequence as:

```text
REVERSIBLE
COMPENSATABLE
IRREVERSIBLE
APPEND_ONLY_CORRECTION
```

The first live slices should prove at least one compensation/recovery path and one pre-execution protection for an irreversible or externally consequential action before broad external autonomy is considered.

## 11. Donor / framework evidence rule

Vendoring is not adoption and architecture resemblance is not value.

For Munder, Plasma or any future donor/framework, adoption beyond a bounded pilot requires a measured comparison against the native AIOS baseline on the same task, including relevant dimensions such as:

```text
correctness
latency
cost
operational complexity
failure behavior
security / authority compatibility
transparency / lineage completeness
maintainability
```

No new major framework is added by default without a measured architectural gap.

## 12. Product / UX boundary

Internal architecture belongs primarily in Cockpit and engineering/transparency surfaces.

`My Mobility` should optimize for the user’s goal:

```text
What can I do?
What am I eligible for?
What is missing?
What should happen next?
What do I need to provide or decide?
```

Users should not need to understand WorkItem internals, A-level terminology, policy fingerprints or lineage graphs to complete a mobility journey.

## 14. Exit criteria for this gate

This gate is not satisfied by creating evaluation schemas alone.

Before another major autonomy architecture expansion, the repository should show evidence of:

1. a versioned mobility evaluation harness with explicit case provenance and denominator-safe metrics;
2. an initial curated Austria benchmark beyond synthetic harness tests;
3. at least one real J→K→L vertical where persistent AI employees cooperate on mobility work;
4. domain-correctness results on that vertical;
5. cost, latency and governance-overhead measurements;
6. Context Broker adversarial results;
7. at least one workflow-level recovery/irreversibility proof;
8. Cockpit visibility into the real organization activity;
9. clear My Mobility UX that does not expose internal architecture unnecessarily;
10. any donor/framework expansion justified by benchmark evidence rather than availability.

The first iterations may be small. The key requirement is that claimed usefulness is measured rather than inferred from architectural sophistication.
